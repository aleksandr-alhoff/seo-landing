Скил проводит AI-агента для кода через полный рабочий процесс создания лендинга:

1. Анализ существующей страницы
2. Исправление проблем технического SEO

4. Улучшение Core Web Vitals
5. Оптимизация изображений и шрифтов
6. Добавление структурированных данных
7. Удаление лишних зависимостей
8. Валидация финальной реализации

## Зачем?

AI может сгенерировать красивый лендинг за секунды.
Проблема в том, что сгенерированные страницы часто содержат:

- лишний JavaScript
- слишком тяжёлые изображения
- слабую семантическую структуру
- отсутствие структурированных данных
- слабые метаданные
- узкие места производительности
- ошибки технического SEO

SEO Landing Skill даёт агенту воспроизводимый рабочий процесс технического SEO вместо опоры на общий промптинг.

Агент-скил, который создаёт и обновляет лендинги с целью **100/100 лабораторного PageSpeed** и производительности, дружелюбной к Core Web Vitals, и делает техническое SEO правильно. Статический HTML, критический CSS, изображения AVIF, полная разметка schema.org, ноль сторонних запросов при первой загрузке (отложенные виджеты, если используются, гейтятся по согласию и документируются в манифесте зависимостей). Это цели оптимизации, а не гарантированные результаты — итог зависит от контента, хостинга, устройств и реального трафика; сам статус Core Web Vitals Google определяет по полевым (RUM) данным, а не по лабораторным инструментам.

## Ключевые требования, которые обеспечивает скил

- **Производительность**: LCP < 2,5 с, INP < 100 мс, CLS < 0,1; критический CSS инлайнится, остальной грузится асинхронно; LCP-изображение грузится сразу с `fetchpriority="high"` (адаптивный preload `imagesrcset`/`imagesizes` — только когда измерение показывает пользу)
- **Изображения**: AVIF → WebP → JPEG через `<picture>`, `srcset`/`sizes`, `width`/`height`, `loading="lazy"` только для изображений ниже фолда (никогда на LCP-изображении), брейкпоинты 320–1920
- **SEO**: title/description/canonical/robots, Open Graph, Twitter Card, JSON-LD (`WebSite`, `Organization`, `BreadcrumbList`, `FAQPage`, `VideoObject` — выпускаются только при подтверждённых фактах и отчитываются согласно выбранному режиму видео, никогда как гарантированная поисковая функция)
- **Доступность**: WCAG 2.1 AA, контраст ≥ 4,5:1, клавиатурная навигация, `prefers-reduced-motion`
- **Безопасность**: `X-Content-Type-Options`, `X-Frame-Options`, `Permissions-Policy`, `Referrer-Policy`, постраничный CSP, поэтапный HSTS, принудительный HTTPS, `rel="noopener noreferrer"`
- **Шрифты**: только системные — никаких внешних шрифтов, никаких Google Fonts
- **Бюджет JS ≤ 15 КБ** на первую загрузку, один файл с `defer`; отложенные сторонние виджеты (если используются) гейтятся по согласию, исключены из бюджета и раскрыты в манифесте зависимостей
- **Запрещено**: внешние JS/CSS-библиотеки, SVG-изображения, синхронные скрипты, iframe при первой загрузке
- **Видео и карты**: паттерн «фасад» по умолчанию — обложка является локальным адаптивным изображением (сразу, если это LCP/выше фолда; лениво ниже фолда), iframe грузится только по клику. Видео только-по-клику обменивает обнаружение видео Google на приватность/производительность до активации; опциональный SEO-обнаружимый режим (самостоятельно хостируемый `<video>` или документированный прямой embed) существует, когда важен видео-поиск (тех-спека §9). Карты остаются только-фасадными.
- **Типовые блоки без JS**: FAQ через `<details>`, слайдер через `scroll-snap`, модалка через `<dialog>`
- **Стоп-точка**: перед валидацией и финальным отчётом скил всегда просит пользователя подтвердить HTML-версию

## Обновление, проверка и удаление установленных копий

Всё ниже определяется двумя фактами:

1. **`git pull` меняет только клон.** Установленная копия, сделанная через `cp -R`, независима — пулл исходного клона НЕ обновляет никакую установку.
2. **`cp -R` копирует, но не синхронизирует.** У GNU `cp` нет поведения синхронизации/удаления назначения: файл, удалённый в апстриме, остаётся в установленной копии навсегда, создавая смешанный релиз из старых и новых инструкций.

Поэтому обновление — это явная, ограниченная, идемпотентная синхронизация в разрешённое назначение скила — никогда слепое повторное копирование.

### Обновление (идемпотентная синхронизация, удаляет файлы, удалённые в апстриме)

Выполняется из директории, содержащей обновлённый клон `seo-landing/`, с `$DEST`, установленным в назначение из таблицы выше:

```bash
DEST=~/.copilot/skills/seo-landing   # ← подставьте нужное назначение

# 1. Сначала восстановление: сделайте бэкап текущей установки (синхронизация деструктивна).
BACKUP=$(mktemp -d "${DEST}.backup-XXXXXXXX") && cp -R "$DEST/." "$BACKUP/" || exit 1
printf 'Backup: %s\n' "$BACKUP"

# 2. Ограниченная идемпотентная синхронизация: копирует новые/изменённые файлы
#    И удаляет файлы внутри $DEST, которых больше нет в апстриме.
#    --delete затрагивает только $DEST.
rsync -a --delete --exclude=.git seo-landing/ "$DEST/"

# 3. Проверка: ноль различий (статус выхода 0), и установленный SKILL.md
#    побайтово совпадает с исходной ревизией.
diff -qr -x .git seo-landing "$DEST" && cmp "$DEST/SKILL.md" seo-landing/SKILL.md
```

Примечания:
- `rsync -a --delete` доступен из коробки на macOS (openrsync) и в типичных системах Linux; `--exclude=.git` не пускает историю клона в установку.
- Бэкап из шага 1 — это путь восстановления: если новая версия ведёт себя плохо, восстановите именно выведенную копию через `rsync -a --delete --exclude=.git "$BACKUP/" "$DEST/"`, предварительно проверив оба пути. Каждый запуск создаёт отдельную копию даже в один день; сохраните `$BACKUP` или выведенный путь для отката. (openrsync на macOS не поддерживает `--backup`, поэтому явное копирование — проверенный механизм.)
- Синхронизацию безопасно перезапускать в любой момент — повторный запуск подряд ничего не меняет.
- Проверенный путь обновления: установка, содержащая файл, который новая ревизия удалила, теряет этот файл после синхронизации, а установленный `SKILL.md` становится побайтово идентичным исходной ревизии.

### Проверка существующей установки в любой момент

```bash
diff -qr -x .git seo-landing "$DEST"
```

Статус выхода `0` (нет вывода) означает, что установка точно совпадает с клоном. Любое напечатанное различие — устаревший, изменённый или лишний файл — перезапустите синхронизацию обновления, чтобы его устранить. Чтобы проверить, какая версия спецификации установлена, прочитайте строку `Version` в начале `$DEST/references/tech-spec.md` (единственный источник истины для версий).

### Перезагрузка / перезапуск после обновления

Агенты читают скилы при старте сессии. После обновления **начните новую чат-сессию** (или перезапустите CLI агента), прежде чем полагаться на новую версию. Клиенты, которые гейтят скилы за доверием/одобрением (например, Hermes: `hermes skills trust`), могут потребовать повторного доверия обновлённой копии.

### Удаление

```bash
rm -rf "$DEST"   # назначение из таблицы выше
```

Если копия была установлена через CLI клиента (`openclaw skills install`, `gemini skills install`), предпочтите собственную команду удаления этого клиента, когда она есть; иначе удаления директории назначения достаточно. Также удалите бэкапы (`$DEST.backup-*`), которые больше не нужны.

### Симлинк-установки — опционально/экспериментально

Симлинк клона в директорию скилов (чтобы `git pull` обновлял его на месте) в принципе возможен, но официальная поддержка симлинков, обработка доверия и поведение перезагрузки различаются по клиентам и здесь НЕ проверены — относитесь к этому как к экспериментальному. Синхронизация через rsync выше — поддерживаемый, клиент-независимый путь обновления.

После установки скил подхватывается автоматически по своему описанию — просто попросите агента «собрать лендинг из брифа с упором на SEO и PageSpeed».

## Использование

1. Дайте агенту бриф: домен, язык (тег BCP-47, базовое направление для RTL-языков и локаль Open Graph — три отдельных входа), тема и ключевые слова, тип бизнеса, CTA и контакты.
2. Скил создаёт отдельную папку проекта (`<workspace>/<project-slug>/`) с `index.html` и каждым локальным ассетом, на который ссылается (все варианты изображений, favicon), плюс — условно — `styles.css` (только отложенный CSS), `script.js` (когда используется JS), `robots.txt`, `sitemap.xml`, `ASSETS.md` и `SERVER-SETUP.md`. Недостающие исходные изображения запрашиваются у пользователя, никогда не выдумываются.
3. На стоп-точке подтвердите HTML-версию — затем скил запускает валидацию (существование локальных ассетов/ссылок, W3C, JSON-LD, Lighthouse как автоматическое доказательство, плюс обязательные ручные проверки доступности) и выдаёт отчёт: LCP, баллы PageSpeed и использованные типы schema.org.
